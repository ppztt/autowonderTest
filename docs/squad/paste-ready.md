# 第一部分：SDLC 流程

新建流程时把「流程描述」贴描述框，「执行说明」贴步骤链编辑器的执行说明列。步骤类型填 `WORK`，必需选「是」。

## 流程 1：需求澄清流程

**流程描述**

```text
根据工单与前后端代码现状明确改动边界、接口契约与可执行验收条件，将需求交给开发。
```

**步骤名称**：拆解需求并交开发

**执行说明**

```text
读取本工单、相关代码与现有接口实现，写明用户目标、改动边界、拆解步骤和可执行的验收条件。

本仓库为前后端同仓的前后端分离项目：前端在 frontend/（React + TypeScript + antd），后端在 backend/（Express + JWT），后端分层为 routes → controllers → services，路由分 backWay/（后台）与 gateway/（网关）两组。

必须产出接口契约表，逐条写明：请求路径、HTTP 方法、是否需要 token、请求体字段与类型、响应结构（成功与失败两种）。纯前端改动明确标注「不涉及接口变更」。契约缺失或含糊是这类仓库最常见的失败原因，没有契约不得进入开发。

基线固定为远端默认分支 main。新需求从 main 切出专属分支 feat/wi-<工单ID>-<主题>，缺陷用 fix/wi-<工单ID>-<主题>；同单返工沿用原分支，不新建。记录目标仓库、基线 SHA 与专属分支名。

本项目为全局 JWT 鉴权，白名单仅 /manage/member/login、/portal/member/login、/portal/member/register 三个路径。新增免登录接口必须修改 app.js 的豁免列表，属高风险改动，须在澄清中单独标注并说明必要性。登录依赖本地 MySQL（127.0.0.1:3306，库 crpp），验收前需确认数据库可用。

验收条件须逐条可验证：前端写浏览器上可观察的结果，后端写具体的 HTTP 请求与期望状态码/响应字段，不接受「接口正常」这类无法判定的表述。

范围明确、不影响实现方案的歧义可直接给出结论并交付；仅当缺失信息会改变接口契约或实现方案时才提问，提问须列出具体缺失项。

在工单简评并将结果保存为 evidence/requirements.md，按当前 Runtime 契约提交产物、checklist 和结构化 handoff，toType=AGENT、nextRole=R2_DEV。

不产出补丁代码，不修改业务文件，只在 evidence/ 下写产物。
```

## 流程 2：开发交付流程

**流程描述**

```text
在专属分支上按接口契约完成前后端成组改动，双端自测通过后交付精确提交。
```

**步骤名称**：实现并交付

**执行说明**

```text
读取本单 evidence/requirements.md 与其中的接口契约，从 main 切出或沿用专属分支 feat/wi-<工单ID>-<主题>，只在该分支提交，分支名与提交信息均带工单号。

按契约同时完成前后端改动：接口变更必须前后端成组提交，不允许只改一侧。前端改动限于 frontend/src 下的 pages、components、api、router、utils、type；后端改动限于 backend 下的 routes、controllers、services、util、config。禁止修改数据库表结构、新增依赖、修改 bin/www 与构建脚本；确需修改时停止并交真人确认。

后端任何新增或修改的路由必须显式说明是否需要 token。若要进入白名单，必须修改 app.js 的豁免列表，并在交付说明中单独列出该改动及理由。

禁止为让测试通过而修改或删除既有断言、添加 skip/only、mock 掉被测逻辑或放宽断言条件。前端测试命令为 npm test -- --watchAll=false；后端没有测试框架，不得声称「后端测试通过」。

交付前必须执行并记录原始输出（命令、退出码、输出尾部不少于三十行）：
- 前端：在 frontend 目录执行 npm run build，并执行 npm test -- --watchAll=false
- 后端：在 backend 目录执行 npm run serve 启动服务，按接口契约逐条发起 HTTP 请求，记录请求命令与响应；未携带 token 的场景必须验证返回 401

将交付记录保存为 evidence/dev.md，包含精确 commit SHA、分支名、基线 SHA、接口契约逐条验证结果与命令原始输出。按 Runtime 契约提交产物、checklist 和结构化 handoff，toType=AGENT、nextRole=R3_REVIEW。

发现契约与实际代码不一致时停止并交回 R1_CLARIFY，不得自行改写契约。
```

## 流程 3：代码评审流程

**流程描述**

```text
对交付的精确提交做独立只读评审，判定是否允许进入验收。
```

**步骤名称**：只读评审

**执行说明**

```text
只读评审。读取 evidence/requirements.md 的接口契约、evidence/dev.md 与交付 commit 的完整 diff，逐条核对。不做任何修改，不产出可直接套用的修复代码。

必查七项，任一项不满足即判定不通过：
1. 契约一致性：diff 中实现的接口路径、方法、入参、出参与契约逐字对照，不一致即为不通过。
2. 成组改动：接口变更必须前后端同时出现，只改一侧视为不通过。
3. 越界改动：出现改动边界之外的文件，尤其 bin/www、package.json、构建脚本、config 下的连接配置。
4. 鉴权绕过：新增接口未说明是否需要 token，或未经说明擅自加入 app.js 白名单。
5. 安全缺陷：SQL 字符串拼接导致注入风险、密码等敏感字段返回给前端、token 未校验直接使用。
6. 错误处理：空 catch 块吞掉异常导致请求无响应，或把内部错误堆栈原样返回给调用方。
7. 证据不足：evidence/dev.md 缺少命令、退出码或接口验证记录。

结论只有通过或不通过。不通过须给出文件与行，并指明违反了哪一条契约或哪一项检查。不得以代码风格、命名、组件拆分建议为由不通过。

将评审结论保存为 evidence/review.md。按 Runtime 契约提交产物、checklist 和结构化 handoff：通过时 toType=AGENT、nextRole=R4_QA；不通过时 toType=AGENT、nextRole=R2_DEV。
```

## 流程 4：验收流程

**流程描述**

```text
在交付的精确提交上启动前后端并逐条验证验收条件，产出可复现的验收材料。
```

**步骤名称**：双端启动并逐条验收

**执行说明**

```text
读取验收条件、交付 commit 与接口契约，在该 commit 上完整启动前后端并逐条验证。

启动阶段：确认本地 MySQL 可用（127.0.0.1:3306，库 crpp）；在 backend 目录执行 npm run serve，后端默认监听 3000；在 frontend 目录执行 npm start，前端默认监听 8080。记录实际端口。

验证阶段只读：仅发起 HTTP 请求、访问页面、查看浏览器控制台，禁止改动代码、提交或修改仓库配置。

必测三类：
1. 鉴权基线：未携带 token 请求任一受保护接口必须返回 401；白名单路径不应被 401 拦截。
2. 契约命中：按契约逐条发请求，比对状态码与响应字段结构。
3. 页面验收：打开受影响页面，确认渲染与交互符合验收条件，记录控制台是否有报错。

任一环节失败立即停止并如实上报，不得以「代码看起来没问题」替代实际调用；不得反复重试直到通过，偶发失败须说明是第几次执行与失败内容。页面正常但控制台报错时判定为不通过。

将结果保存为 evidence/verify.md，包含：可复现的双端启动步骤、每条请求的命令与响应摘要、页面验收清单、以及一条最小复现路径。按 Runtime 契约提交产物、checklist 和结构化 handoff：通过时 toType=AGENT、nextRole=R5_MERGE；不通过时 toType=AGENT、nextRole=R2_DEV；需要人工判断时 toType=HUMAN。
```

## 流程 5：分支合并流程

**流程描述**

```text
汇聚已通过独立验收的候选分支，复现并分级冲突，验证集成结果后合并主干。
```

**步骤名称**：溯源校验与合并

**执行说明**

```text
读取 evidence/review.md 与 evidence/verify.md，核实上游交付，风险分级，正常合并，远端回读。

溯源校验：功能提交必须可追溯到本单开发角色的派发，且取得该提交的独立验收通过记录；核对工单明确排除的分支或提交没有进入候选历史。

交付分支上若存在评审或验收角色产生的提交，视为证据污染，拒绝合并。

只处理明确的机械性冲突（导入顺序、格式、相邻无关改动）。涉及功能语义、接口契约或数据库字段的冲突不得自行裁决，交回开发角色或真人。

合并目标为 main。合并后必须在远端回读结果，并在合并结果上重新执行：前端 npm run build、后端启动并用契约中的关键接口做一次冒烟，任一失败不得宣告完成。

将合并结果保存为 evidence/merge.md，记录合并前后 SHA、回读结果与两项验证的输出。按 Runtime 契约提交产物、checklist 和结构化 handoff：完成时按平台约定终态提交；需要人工决策时 toType=HUMAN。
```

# 第三部分：检查项与策略建议

平台两列的实际字段我未见过，以下按功能意图给建议，字段名以界面对应为准。

| 流程 / 步骤 | 检查项 | 策略 |
|---|---|---|
| 需求澄清 | evidence/requirements.md 存在且含接口契约表 | 契约缺失则不进入开发 |
| 开发交付 | 前端 build 与 test 退出码为 0；evidence/dev.md 含 commit SHA 与接口验证记录 | 任一项不满足不进入下一环 |
| 代码评审 | evidence/review.md 存在且结论非空 | 不通过回到开发，限制重试轮次（建议 2 轮后转人工） |
| 验收 | evidence/verify.md 含双端端口、curl 命令与响应摘要 | 不通过回开发；需人判断时转人工 |
| 分支合并 | main 上前端 build 通过、后端启动冒烟通过；溯源链完整 | 溯源断裂或语义冲突时转人工 |
