# 自造工单（基于实测代码）

工单按「不依赖数据库数据」优先排序 —— 因为 `crpp` 库里未必有可用数据，验收条件必须能在空库下执行。

判断标准只有一条：**验收条件能在命令行或浏览器里执行出 yes/no**。

---

## 工单 1：后端新增健康检查接口（跑通链路专用）

| 项 | 值 |
|---|---|
| 难度 | 低（1-2 个文件） |
| 覆盖 | R1 → R2 → R3 → R4 → R5 全链路 |
| 依赖 | 无 |

**背景**

后端目前没有任何免登录的可用性探测接口，前端和运维都无法判断服务是否正常。现有全局 JWT 中间件会让所有请求返回 401，包括根路径。

**期望行为**

1. 新增 `GET /portal/health`，返回 `{ "status": "ok", "time": "<ISO 时间字符串>" }`。
2. 该接口**免登录**，不需要 token。
3. 其余接口的鉴权行为不变。

**验收条件**

| # | 操作 | 期望结果 |
|---|---|---|
| 1 | 改动前请求 `curl -s -o NUL -w "%{http_code}" http://localhost:3000/portal/health` | 返回 `401`（说明当前被全局中间件拦截） |
| 2 | 改动后同一请求 | 返回 `200` |
| 3 | `curl -s http://localhost:3000/portal/health` | 响应体含 `"status":"ok"` 且有 `time` 字段 |
| 4 | 请求一个受保护接口 `curl -s -o NUL -w "%{http_code}" http://localhost:3000/manage/member/get_member_list` | 仍返回 `401`（白名单没被放宽） |
| 5 | 后端启动日志 | 无报错，进程持续存活 |

**关键点**

第 4 条是重点：它检验的是「改白名单时没有顺手把鉴权搞坏」。这是本项目最容易出的事故。

## 工单 2：前端新增页面并注册路由（纯前端）

| 项 | 值 |
|---|---|
| 难度 | 中低 |
| 覆盖 | 验 R1 的影响面分析（要同时找到 page 与 router 两处） |
| 依赖 | 无 |

**背景**

后台侧缺少一个「关于/版本信息」页面。

**期望行为**

1. 在 `frontend/src/pages` 下新增一个页面，页面显示固定标题 `About`、一行说明文字和当前时间（进入时刷新）。
2. 该页面注册到 `frontend/src/router/routes.tsx`，可通过 URL 直接访问。
3. 页面可从侧边菜单进入（若菜单由路由配置驱动则自动生效，否则需补充菜单项）。

**验收条件**

| # | 操作 | 期望结果 |
|---|---|---|
| 1 | `npm run build`（在 frontend 目录） | 退出码 0 |
| 2 | `npm start` 后直接访问该页面路径 | 页面渲染出 `About` 标题 |
| 3 | 查看页面 | 显示的时间是当前时间，不是硬编码字符串 |
| 4 | 从菜单点击进入 | 能跳转到该页面 |
| 5 | 浏览器控制台 | 无红色报错 |
| 6 | `git diff --stat` | 只动了 pages 下新文件与 router 相关文件，未改后端 |

## 工单 3：前端状态页调用后端健康接口（双端契约）

| 项 | 值 |
|---|---|
| 难度 | 中 |
| 覆盖 | 重点验**接口契约**：前端调用方式与后端返回结构必须对齐 |
| 依赖 | 工单 1 已完成 |

**背景**

前端需要能直观看到后端服务状态，避免出问题时反复猜测。

**期望行为**

1. 新增一个状态页，页面加载时请求 `GET /portal/health`。
2. 请求成功显示「后端正常」及返回的时间；请求失败显示「后端不可达」。
3. 请求通过项目既有的 api 封装发起，不在组件里直接写 `fetch` 地址。

**验收条件**

| # | 操作 | 期望结果 |
|---|---|---|
| 1 | 后端启动、前端启动，打开状态页 | 显示「后端正常」与后端返回的时间 |
| 2 | 停掉后端进程后刷新页面 | 显示「后端不可达」，不白屏、不卡死 |
| 3 | 浏览器 Network 面板 | 请求地址为 `/portal/health`，状态码 200 |
| 4 | 检查代码 | 未在组件内硬编码完整 URL，复用了 `frontend/src/api` 下的封装 |
| 5 | `npm run build` | 退出码 0 |

**关键点**

第 2 条最容易失败：多数实现只写成功分支，后端挂掉时页面直接抛错白屏。

## 工单 4：清理后端未被引用的脚手架路由（缺陷清理）

| 项 | 值 |
|---|---|
| 难度 | 低 |
| 覆盖 | 验 R2 的范围控制与 R3 的越界检查 |
| 依赖 | 无 |

**背景**

后端 `routes/index.js` 与 `routes/users.js` 是 Express 脚手架残留，`app.js` 中对应两行引用已被注释。这两个文件仍在仓库里，容易误导后续开发以为有可用路由。

**期望行为**

1. 删除这两个未被引用的路由文件（或按澄清结论处理）。
2. 不得改动 `app.js` 中已注释的引用行以外的任何鉴权逻辑。

**验收条件**

| # | 操作 | 期望结果 |
|---|---|---|
| 1 | `git diff --stat` | 只有删除，且文件数 ≤ 3 |
| 2 | 后端启动 | 正常监听 3000，无 `Cannot find module` 报错 |
| 3 | `curl http://localhost:3000/manage/member/get_member_list` | 仍返回 401（鉴权未被影响） |
| 4 | 全局搜索 `require.*routes/index` 与 `require.*routes/users` | 无残留引用 |

**关键点**

验收条件 3 是防止「清理顺手把鉴权中间件也动了」。

## 工单 5：登录页空输入校验（纯前端）

| 项 | 值 |
|---|---|
| 难度 | 中低 |
| 覆盖 | 重点验 R4 的页面验收 |
| 依赖 | 无（不发请求即可验证） |

**背景**

登录页在账号或密码为空时仍会提交请求，用户看到的是后端反回的模糊提示甚至无响应。

**期望行为**

1. 账号或密码为空时点击登录，不发起请求，页面上给出明确提示。
2. 两项都填写后才允许提交。
3. 提示文案与页面既有风格一致（使用 antd 的反馈组件）。

**验收条件**

| # | 操作 | 期望结果 |
|---|---|---|
| 1 | 两项均留空点击登录 | 停留当前页，出现提示；Network 面板**无**登录请求 |
| 2 | 只填账号、密码留空点击登录 | 同上 |
| 3 | 两项都填写后点击登录 | 正常发起请求（Network 可见） |
| 4 | 浏览器控制台 | 无红色报错 |
| 5 | `npm run build` | 退出码 0 |

**关键点**

第 1 条的「Network 无请求」是关键：只加了视觉提示但仍在发请求的实现，在这里会被抓出来。

## 使用建议

| 阶段 | 用工单 | 看什么 |
|---|---|---|
| 第 1 次跑通 | 工单 1 | 五角色能否串起来，重点看工单 1 的第 4 条验收会不会被漏 |
| 练 R1 影响面 | 工单 2 | 是否同时定位到 page 与 router 两处 |
| 练接口契约 | 工单 3 | 前后端是否成组改，失败分支是否实现 |
| 练范围控制 | 工单 4 | 会不会顺手改动 `app.js` 的鉴权逻辑 |
| 练 R4 | 工单 5 | 有没有真去点页面看 Network，还是只跑了 build |

工单 4 适合放在中间：改动小、验收硬，能快速判断 R3 的越界检查是否真的生效。
